# Header Search — E2E Scenario Doc

Test file: `client/e2e/header-search/header-search.e2e.ts`.
Matrix source: `docs/specs/header-search/design.md` § "E2E Scenario Matrix" (rows 1-12).

Feature is **read-only** (search + external app open via `window.open`; "View
All" is a client-side navigation to `/apps?search=<q>`). No data mutation, so
no revert step is needed and the "mutation-heavy" Gate-B carve-out (§4.3) does
not apply — all rows run under Gate A + Gate B.

## Deferred / follow-up items (not blocking, flagged per client CLAUDE.md §4.3 selector rule)

1. **`aria-live` announce region not directly asserted.** `useAnnounce` fires `dashboard.header.announce.results` / `announce.noResults` / `announce.opened` into a live region, but no test locates that specific `aria-live` node and asserts its text content changes on each state transition — the visible popover text (which uses the same translated strings) is asserted instead. Follow-up: add a `page.locator('[aria-live]')` assertion once the concrete `useAnnounce` DOM implementation/selector is confirmed (no `data-testid` currently on the live region — would need one added to `useAnnounce`'s host element, which is out of scope for this E2E-only task since it requires an app-code change).
2. **`viewAll`/`openLabel` Vietnamese strings not independently re-asserted.** Row 9's VI test does not additionally open a query with an above-limit total and click "View All" in Vietnamese — English coverage exists via row 7. Low risk (same i18n key resolution mechanism already verified for 3 other keys in VI); can be folded into a future i18n suite expansion if this key regresses.
3. **Mobile search button behavior is intentionally out of scope.** Per design.md §6 ("Mobile: search button hiện tại giữ nguyên ... flag follow-up"), the mobile search icon button remains a no-op placeholder — not wired to `HeaderSearch` in this feature, so no E2E scenario targets it. This mirrors the design doc's own explicit scope cut, not a testing gap.
4. **Selector note (no data-testid needed):** all selectors used are role/label-based (`getByRole("combobox")`, `getByRole("listbox")`, `getByRole("option")`, `getByText` for i18n strings) per the client CLAUDE.md §4.3 selector preference. The implemented DOM (`role="combobox"` forwarded through `SearchInput`/`CustomInput` to the native `<input>`; `role="listbox"`/`role="option"` on `ResultList`/`ResultRow`) supports this fully — **no `data-testid` fallback was required** for this feature.
5. **BVA "total = limit vs total > limit" and the null-category row use `page.route` stubs, not live seed data.** The current E2E seed (Blog/Notes/IDMS Portal — 3 user-visible apps) cannot reliably produce a `total` crossing `HEADER_SEARCH_RESULT_LIMIT = 5`, nor a null-category app, so these two boundary/edge cases are verified deterministically via response interception rather than depending on seed data shape. If the seed is later extended to include ≥6 user-visible apps and/or a null-category app, these could be converted to live-data assertions, but the stubbed version is equally valid evidence for the FE behavior under test.
6. **Race/dedupe-by-query-key (matrix row 11, "response cũ không đè query mới") is not independently stress-tested** beyond the debounce-timing test (row 6) which already exercises rapid sequential input. A dedicated slow-then-fast response race (older request resolving after a newer one) was not added — React Query's query-key cache is a well-established library guarantee here, not app-specific logic; flagged for awareness only, not blocking.

## Fix log

- **2026-07 — popover open/close + width fix** (`fix/header-search-popover`): first click on the (unfocused) input opened then immediately closed — the `PopoverTrigger` built-in click-toggle fought the `onFocus`-open. Fixed by switching to `PopoverAnchor` (no click-toggle) + explicit focus/click open handlers. Also the content width class `w-[--radix-popover-trigger-width]` (Tailwind v3 shorthand) was inert under Tailwind v4 → popover fell back to the shadcn default `w-72`; changed to `w-[var(--radix-popover-trigger-width)]` so the popover matches the input width. Added regression test **"single click opens the popover and it stays open [regression: no toggle-close]"** (Row 1 area) asserting the popover stays open after click, closes on Esc, and reopens on click.
